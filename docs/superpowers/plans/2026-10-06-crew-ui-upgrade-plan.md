# Crew 商家工作台 UI 修改计划

日期：2026-10-06。状态：用户批准的阶段 1–5 已完成开发与自动验证，人工体验反馈待记录。实施结果见 `docs/commerce/crew-ui-upgrade-acceptance-2026-10-06.md`。

目标：让独立站商家进入 Crew 后，能判断当前店铺进度、找到下一步、审查团队成果，并完成建站或新品上线。延续 `Crew — Your AI commerce team.` 定位，保留独立编程能力。

架构：沿用 React、TypeScript 和 Python API。复用现有四列看板、任务详情侧栏、审查组件及共享主题，先重组入口和业务流程，再增加上下文助手。产品范围仍为 WordPress/WooCommerce、店长／网站开发／商品内容三个角色。

本计划基于当前项目代码、实际浏览器截图以及竞品的官方公开页面和帮助文档。没有进行竞品登录后台的完整实测；部分官方图片无法读取，不作像素级一致性判断。下列布局与尺寸是 Crew 的设计建议，不是竞品参数。

## 竞品分析与取舍

| 产品 | 官方资料支持的交互特点 | Crew 建议采用 | 首版边界 |
|---|---|---|---|
| 10Web | 建站依次经历描述商店、结构与风格、生成与调整 | 把现有表单组织成能返回修改的步骤，持续展示店铺预览和准备状态 | 不扩展成任意 WordPress 页面可视化编辑器 |
| Replit Agent Task Board | Drafts、Active、Ready、Done 四列；草稿先审计划，完成后查看日志、测试与预览，再应用 | 保留现有四列；突出业务标题、下一步和待处理原因；保留侧栏审查 | 代码整合与店铺发布分别授权，不能把 Done 等同于已发布 |
| Shopify Sidekick | 可在店铺各页面打开对话，利用当前页面上下文，提出操作供商家审查 | 同一个店长助手跟随网站、商品和任务页面；显式显示当前店铺与所选对象 | 不推导出 Crew 已有订单、客服或营收分析能力 |
| Linear | 列表与看板视图切换、可配置显示信息，以及查看条目详情的 Peek | 压缩卡片信息；增加列表视图、快速查看；保留返回后的位置和筛选 | 不照搬研发项目管理的复杂层级和所有快捷键 |

来源：[10Web 电商建站](https://10web.io/ai-ecommerce-website-builder/)、[Replit Task Board](https://docs.replit.com/features/agent/task-board)、[Sidekick 使用方式](https://help.shopify.com/en/manual/ai-powered-tools/sidekick/set-up)、[Linear 显示选项](https://linear.app/docs/display-options)、[Linear Peek](https://linear.app/docs/peek)。公开 UI 可能随版本和分批发布变化。

研究结论：Crew 应组合结构化建站、任务看板和店铺上下文助手。下一轮优先改善信息组织，保留当前灰白基底、深灰文字和紫色强调，避免再次整体更换视觉方向。

## 建议的信息架构

全局只保留一条主侧栏，顶部放店铺切换器。进入某个店铺后，页面内用标签或工具栏区分子功能，不再并排放第二条完整侧栏。

```text
Crew
店铺切换
  概览
  网站
  商品
  团队任务

开发空间
设置
  店铺连接与环境
  品牌资料
  偏好与记忆
  模型与用量
  项目资料导出与恢复
```

“模型与用量”只展示服务已经提供的数据；无法计算的费用显示“暂不可用”，不显示估算为零。项目资料导出沿用现有范围，不改称完整店铺备份。

开发空间无需先创建店铺，保留编程、研究、资料整理和通用任务。任务可关联商家项目，但不能在切换店铺后悄悄改变原任务的工作区。

## 核心页面设计

### 商家概览

首屏按以下顺序呈现：店铺名称与真实连接状态；需要处理的任务；建站／新品上线两个明确入口；最近任务与可用网站预览。未有真实经营数据时，不展示销售额或转化率仪表盘。

新用户显示简短的准备清单和创建店铺入口；已有店铺显示业务进度。大幅抖色插画仅用于初次引导和空状态，日常页面以任务和成果为主。没有截图时显示准备步骤；有截图时标明生成时间和对应版本。

店长助手用一个明确按钮打开，首页可提供简短目标输入。输入提交前显示当前店铺及所选对象；“准备计划”和“开始执行”区分，后者沿用预算、权限与审批机制。

### 建站与新品上线

建站引导：品牌资料 → 页面结构与风格 → 团队执行 → 预览与验证 → 审查发布。

新品引导：商品资料／图片 → 文件校验与内容确认 → 团队准备 → 变更审查 → 发布结果。

每一步展示已完成、进行中、待补充或失败状态，提供一个主要按钮。允许返回修改，自动解释受影响的后续步骤；项目版本变化后，不能继续使用已失效的验证或发布批准。纯文件校验不标为已上线。

字段级错误紧邻输入项，顶部给出简短汇总；CSV 提供上传文件、格式示例和错误行定位，继续支持原文本方式。政策、支付、运输等商家事实不能由模型编造。

### 团队任务与成果审查

保留四列看板，增加列表切换；手机默认列表。卡片默认展示业务标题、角色、状态、下一步或阻塞原因；编号与版本移到次要位置。初版角色只取已有三角色绑定，未知角色不猜测。

沿用现有详情侧栏和“任务进度／成果审查／后续任务”，不重写一套任务系统。概览先给出“完成了什么、仍缺什么、需要你决定什么”。代码、日志和原始角色提示放入明确的技术明细入口，完整保留内容。

发布区域始终显示目标店铺、环境、变更范围及批准版本；用“批准本次发布”“执行已批准步骤”等具体动作名称。未知结果显示“核对结果”，不提供可能重复写入的盲目重试。

### 店长助手

桌面使用可关闭的右侧面板，平板根据宽度切换并排或覆盖，手机使用全屏对话。只设一个协调入口；网站开发、商品内容作为任务里的角色呈现。

这是包含功能接线的 UI 阶段：需要定义所选页面／对象如何进入上下文、任务如何关联，以及完成后如何返回成果。先复用现有项目资料和受限工具；若无法安全完成绑定，则显示明确的选择步骤，不能只做一个无实际能力的聊天外壳。

### 偏好与记忆

设置中展示已确认记忆、待确认候选、作用域及删除／撤回。自动维护开关沿用原默认值与配置。品牌和商品的正式资料仍在对应业务模块管理；不把价格、库存或发布许可变成自由文本记忆。

## 视觉与交互规范

- 保留背景 `#F6F6F7`、白色卡片、文字 `#242424`、辅助文字 `#666666` 和强调色 `#6941C6`。成功、警告、失败用语义颜色配文字，不能仅靠颜色区分。
- 正文建议 14–16px，辅助信息通常不低于 12px；页面标题 24–28px。中英文使用同一无衬线字体系统，代码区保留等宽字体。
- 使用 8px 间距基准，页面内边距建议桌面 24–32px、手机 16px；卡片圆角 10–12px。每个主要任务区域突出一个主动作。
- 抖色图形集中于品牌与空状态；加载和按钮反馈采用约 120–180ms 的轻动画，遵循 reduced-motion。
- 正文对比度按 [WCAG 2.2 AA 最低对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)要求检查，普通文字至少 4.5:1。移动端关键触控区域建议至少 44×44px。
- 表格／代码允许区域内横向滚动，页面本身不能横向溢出；窄屏保留文字导航或明确菜单，不能完全依赖无提示图标。
- 所有新增固定文案进入现有中英文词典；品牌、商品、用户输入与模型产物保持原文。

## 分阶段实施与验收

以下为单名前端开发、主要复用现有 API 的工作量粗估，不是交付承诺；上下文助手与路由接线需要先验证接口，可能增加时间。先完成桌面主流程，再适配平板和手机。

| 阶段 | 优先级 | 产出 | 粗估 | 阶段验收 |
|---|---|---|---|---|
| 1 导航与首页 | P0 | 单一侧栏、店铺切换、商家首页、开发空间、设置内的记忆入口 | 2–3 工作日 | 能直接找到建站、上新、待处理任务；无店铺仍可编程；刷新／返回不串店铺 |
| 2 两条业务流程 | P0 | 分步引导、表单反馈、真实状态与下一步 | 3–4 工作日 | 返回修改不丢输入；资料过期正确阻塞；建站／上新都能从入口走到现有审查页 |
| 3 任务与审查整理 | P1 | 卡片信息层级、列表视图、业务摘要、技术明细折叠 | 2–3 工作日 | 筛选与滚动位置保持；取消／批准／未知结果行为无回退；旧任务仍可查看 |
| 4 上下文店长助手 | P1 | 页面内助手、明确对象绑定、成果入口 | 3–5 工作日 | 不混用店铺数据；生成计划与执行区分；不因打开或切换页面调用模型 |
| 5 适配与体验验收 | P0 交付门槛 | 桌面／平板／手机、中英文、键盘操作与空／错／加载状态 | 2–3 工作日 | 通过下列验收清单并获得人工反馈 |

合计约 12–18 个工作日。阶段 1–3 优先构成可交付的 UI 版本；阶段 4 可单独上线，但阶段 5 中相关检查必须随每批变更执行。工程量在导航与上下文接口试接后重新估算，不新增营销、订单、分析等业务模块。

## 开发落点

实现时使用现有开发副本 `outputs/muse-next`；先检查工作区未提交改动，再分批集成。

| 阶段 | 主要文件或组件 | 接口与实现重点 |
|---|---|---|
| 1 | `frontend/src/main.tsx`、`commerce/CommerceHome.tsx`、拟新增 `AppNavigation.tsx` 与 `commerce/MerchantOverview.tsx` | 建立显式视图、项目与任务身份；区分未登录、无店铺、已有店铺；业务视图与技术任务入口相互返回 |
| 2 | `commerce/SiteWizard.tsx`、`SiteBlueprint.tsx`、`ProductImport.tsx`、`ProductImages.tsx`、`StoreTeam.tsx` | 复用已生成 API 类型与版本字段；步骤本身不制造第二份业务状态；审查批准继续由后端判断 |
| 3 | `commerce/TaskBoard.tsx`、`WorkspaceDialog.tsx`、`ReviewWorkspace.tsx`、`ReviewSummary.tsx`、`MerchantRelease.tsx` | 同一任务同时支持列表与看板；技术明细折叠只改变展示；保留已实现的离开页面停止后续发布行为 |
| 4 | 拟新增 `commerce/ManagerPanel.tsx` 与现有任务上下文接口 | 先定义项目 ID、对象 ID、请求版本和任务 ID 绑定；用户可见的上下文来自服务端有效记录；不让客户端任意扩大工具权限 |
| 5 | `theme.css`、`style.css`、`commerce/studio.css`、`i18n/`、相关浏览器测试 | 延续共享样式变量；删除不再需要的覆盖；保证首次加载和切换后的样式一致 |

新组件名称为建议，实施时按最终拆分确认。现有 API 若缺少某项视图数据，先明确增加只读响应的范围和权限，不将前端临时拼接视为可信业务状态。

执行每一阶段时：先检查现有流程及失败边界；对状态切换、跨项目隔离和发布行为写有意义的回归用例；实现后运行受影响测试并检查真实截图；记录完成项和剩余问题。纯样式和文案通过构建、截图及现有交互验证，不为每个 CSS 属性新增测试。

## 验收清单

- [x] 从登录后的首页可直接进入建站或新品上线，常见入口不超过两次点击。
- [x] 待处理任务数量与服务端一致，点击可到具体原因及下一步；空列表不制造虚假统计。
- [x] 浏览器刷新、返回和切换项目后不会落到其他项目的任务；未保存输入按明确规则保留或提示。
- [x] 无店铺时仍可进入编程、研究和资料整理；原任务、日志、审批和成果均可访问。
- [x] 记忆入口迁移后可以读取原记忆，作用域和撤回行为不变。
- [x] 发布前能看到目标环境与变更；旧批准、版本变化、未知写入结果正确阻塞。
- [x] 任务异常分别呈现排队、等待输入、等待审批、模型失败、验证失败和结果待核对，提供有效动作。
- [x] 1440／1280／900／390／360px 宽度无页面级横向溢出；关键弹窗操作在手机可见。
- [x] 中英文覆盖新文案，无截断关键按钮；切换语言不丢输入、不改变商家内容、不产生写请求。
- [x] 键盘焦点可见，弹窗焦点可恢复；登录语言按钮、任务抽屉和移动导航可实际点击。
- [x] 前端构建及相关浏览器回归通过，截图包含有数据、空状态、长标题和失败状态。
- [ ] 人工尝试三个任务：找到待处理事项、创建建站草稿、审查新品变更。记录完成时间、错误点击与求助次数，作为下一轮改进基线，不冒充已有 benchmark 成绩。

阶段 1–5 已按本计划实施。完整浏览器回归 56 项通过，最终受影响用例 18 项复测通过，另补充 1 项长标题与错误状态检查；18 项复测与完整回归有重叠，不相加为独立用例数。前端构建通过。下一步通过本机预览完成上述三个任务的人工体验，记录完成时间、错误点击和求助次数。
