# MUSE 类个人助手与 Java 运行时完全替代：剩余工作计划

> **For agentic workers:** 执行时使用 `superpowers:executing-plans`，按下列复选项推进。本文是基于现有证据的总计划；修复具体缺陷时先补失败用例，再改实现并复测。默认在当前工作区执行，不自动创建新任务或委派子代理。

**日期与状态：** 2026-09-27；计划已编写，下面未勾选的项目尚未完成。现有 RC7 的发布结论是 **NOT_ACCEPTED**，不能把“Python 已可运行”写成“Java 已验收替代”。

**实施更新：** RC8 的质量模型已固定为 `gpt-6-sol`，启动器默认值同步为 Sol；`gpt-6-luna` 保留显式经济试用入口。下面“当前”列及原 Mini 建议保留计划形成时的历史背景，不表示可合并不同模型成绩。最终验收仍必须针对同一冻结候选重跑并完成独立 Windows 与人工门槛。

**目标：** 交付本地单用户 MUSE：Python Agent 核心保留编程能力，并可做带来源的网页研究、资料整理、可恢复后台任务；具备长期事实保留、MCP 按需加载和可控授权。发行包安装、启动、执行与恢复均不依赖 JVM、Java 或 Gradle。网页继续使用 React/TypeScript；“替代 Java”指运行时与产品能力，不禁止助手修改 Java 项目。

**基线与标准：** [原修改计划](../../../../MUSE项目修改计划.md)、[Java 替代方案](../../../../MUSE基于mewcode-python的替代方案.md)、[测试与 Benchmark 标准](../../../../MUSE测试与Benchmark标准.md)、[RC7 验收记录](../../release-acceptance.md)、[模型试验](../../model-cost-selection.md)、[人工评分清单](../../manual-benchmark-handoff.md)、[独立 Windows 清单](../../clean-windows-acceptance.md)、[Java 行为矩阵](../../java-migration-matrix.csv)。前三个链接是相对于本文件所在目录的路径；实施前应核对链接与文件位置。

## 不变约束与判定规则

- 保留原 StarCode 的 API 地址、代理和凭据来源；不修改原配置或发送密钥。真实模型试验用合成夹具；真实项目文件外发只在原先明确授权的范围内。
- 当前 `Start-MUSE.ps1` 默认 `gpt-6-luna`，原配置是 `gpt-5.4-mini`。发布前固定**一个候选版本和一种验收模型策略**：推荐先用原 Mini 完成质量验收，Luna 作为独立的经济模式验收；若决定以 Luna 为默认正式模型，它必须独立通过同一套门槛。两种模型、两版代码或中断前后的成绩不得拼接。预算默认 40 模型轮次、100 工具调用、900 秒活动时间；任何调整在运行前记入 manifest。
- 每次改产品源码、提示、模型选择、工具定义或预算，建立新候选并重跑受影响门槛；最终 60 次业务基准、独立机安装与交付包必须指向同一冻结源码/配置。旧失败原样保留。
- 源项目、数据和旧包只读保存。主许可证未核实前，只做本地候选交付，不公开分发。不得把 Windows 进程控制描述成操作系统级文件/网络沙箱。
- 本计划的“类似 Muse”只指上述用户已确定的本地个人助手能力；支付、邮件自动发送、移动端、语音、多用户 SaaS、云虚拟机与 OCR 均不在首版验收范围。

## 阶段 1：冻结需求、差异与模型策略（P0，约 0.5—1 工作日）

**涉及：** `docs/java-migration-matrix.csv`、`docs/java-behavior-audit.md`、`docs/model-cost-selection.md`、`docs/release-development-ledger.md`。输入是原 Java 行为、用户的 MUSE 首版需求与当前 Python 代码；输出是可逐项检查的候选范围和模型/预算 manifest。

- [ ] 核对 Java 模块矩阵：每项标为已由 Python 覆盖、行为改变且需说明、未覆盖；不能仅凭文件数量关闭条目。核对终端命令、配置、会话/记忆、Hook/Skill、MCP、团队、工作树、文件历史与审批。
- [ ] 将研究、资料、编程三类真实成果，以及进度、停止/继续、历史、下载、记忆、权限和用量逐一对应到入口与测试。已有实现只作基线，不重复造功能。
- [ ] 固定正式质量模型（建议原 `gpt-5.4-mini`）和经济模式测试边界。保留 `gpt-6-luna` 试测 D01 格式差异、C01 漏列 `settings.py`、P01 环境阻塞的原始结论；在正式模型选择前不能将其 17/20 自动预筛当作通过。
- [ ] 将 9 次对 8 次审批的差异写入验收合同：若“完全替代”要求相同会话授权体验，则实现安全等价后复测；若接受更细粒度授权，则明确记为行为改变，不能声称旧数值达标。

**阶段出口：** 同一候选的功能范围、模型、预算、权限契约清楚；所有 Java 条目有可追溯结论。

## 阶段 2：先关闭确定的产品缺陷（P0，约 2—4 工作日）

**涉及：** `src/muse/extensions/worktrees.py`、`src/muse/extensions/teams.py`、`src/muse/tasks/delegation.py`、`src/muse/agent/loop.py`、`benchmarks/multi_agent_python.py`；相关 `tests/`。仅在复现表明需要时修改实现。

- [ ] 用 RC7 的 checkout 与 numeric 原始轨迹定位整合失败：区分子任务未提交、提交未合并、非快进冲突、主任务漏审和验证器失败；先写能失败的回归测试。
- [ ] 修复两个真实子任务独立工作树的提交、消息/等待、主任务复核、冲突处理和最终统一验证。测试故意漏掉任一子提交时必须失败；失败与取消不得丢弃工作树或伪报成功。
- [ ] 同时检查 Luna C01 漏列文件是否属于模型质量、检索覆盖或结果验证问题。若是系统问题，补覆盖测试并修复；若是模型能力问题，不改冻结评分标准，正式验收选通过门槛的模型。
- [ ] 用冻结的 checkout、numeric、text 三题真实模型复测：每题两个子任务有提交与执行时间重叠，主任务整合后统一测试通过，达到 **3/3**。保存任务 ID、提交、时间线、验证退出码与用量。

**阶段出口：** 多 Agent 原指标 3/3；任何失败仍留在报告中，修复后重新形成候选。

## 阶段 3：补齐长期事实、MCP 与核心安全回归（P0，约 1—2 工作日）

**涉及：** `src/muse/agent/context.py`、`src/muse/extensions/mcp.py`、`src/muse/tools/registry.py`、`src/muse/permissions/`、`benchmarks/long_context_python.py`、`benchmarks/mcp_paired_python.py` 及现有测试。

- [ ] 全量回归压缩/检索/重启：事实更正按最新值、原文仍可追溯、跨任务隔离、恢复不重放副作用。按原口径分别完成 **100K、200K、300K** 三次完整长上下文运行与检查点核对。
- [ ] 检查 MCP 的 discover/search/load/call：仅显式配置的服务、按需加载 schema、跨任务隔离、审批绑定、旧目录缓存、超大 schema、恶意工具描述及远端失败。相同 100 工具/十题/同模型条件下跑 **FULL 10/10、LAZY 10/10**，同时报告质量、总 token、耗时与额外调用；不能只看初始 schema 节省。
- [ ] 复测路径穿越、绝对路径、junction、文件符号链接、审批参数变化、重复/过期批准、工具注入、取消与 Worker 重启。开发机无法建文件符号链接时保留 BLOCKED，由阶段 6 在独立机实测，不能写为 PASS。
- [ ] 运行全量 pytest、Ruff、OpenAPI 类型同步及前端构建；保存版本、退出码和失败/跳过清单。第三方弃用警告单独记录。

**阶段出口：** 已能本机验证的必测项无失败；长上下文和 MCP 原指标在同一候选完成；环境阻塞显式保留。

## 阶段 4：冻结候选并做本地可安装交付（P0，约 1 工作日）

**涉及：** `pyproject.toml`、`uv.lock`、`hatch_build.py`、`Start-MUSE.ps1`、`Setup-MUSE.ps1`、`README.md`、`docs/python-runtime-operations.md`、`benchmarks/release_manifest.py`。

- [ ] 提交源码后冻结版本、提交号、模型、提示、夹具、工具、预算、依赖锁与运行顺序；生成脱敏 manifest。原 StarCode 配置和密钥不入包、不入报告。
- [ ] 同一提交构建网页资源、wheel、源码 ZIP 和 SHA-256 清单。检查无 Java/JAR/class/Gradle 运行依赖、数据库、虚拟环境或私人配置。
- [ ] 在全新本地虚拟环境、Java/Javac/Gradle 不在 PATH 的条件下安装同一 wheel，验证 API、Worker、网页、终端、停止/恢复、三类任务最小闭环。核对数据备份、新目录恢复、旧库升级与回滚副本。

**阶段出口：** 有可复现的候选包与哈希；此时仍只是 RC，不能因为本机安装成功就宣布验收。

## 阶段 5：同一候选的正式自动 Benchmark（P0，约 1—3 工作日，取决于模型服务）

**涉及：** `benchmarks/run.py`、`benchmarks/controls.py`、`benchmarks/quality.py`、`benchmarks/release_manifest.py`、`reports/release-candidate/<候选>/`。

- [ ] 先验证评测器能识别缺证据、危险副作用、固定分母、无效运行和资源中断；冻结 20 场景、三轮预定顺序、审批脚本与预算。假模型成绩只用于评测器自检。
- [ ] 用同一冻结候选和正式模型完成 **20 × 3 = 60** 次真实尝试；每轮从干净夹具开始，保存输入、配置、代码哈希、动作轨迹、断言、文件成果、用量及失败。服务错误按协议保留，不用旧 RC6/RC7 或 Luna 先导成绩补位。
- [ ] 自动核查关键安全/完整性断言和类别门槛：每轮 ≥18/20；R、D、C 各 ≥3/4，B、P 均 4/4；BLOCKED 与 NOT_RUN 均为 0；三类真实成果各至少一个成功样例。G1—G8 必须同时成立。自动文本匹配只生成“待人工复核”，不直接签发 PASS。
- [ ] 同时保留原多 Agent、长上下文、MCP、180 动作权限回放和本地性能记录；价格、token、速度、8 小时耐久或加速比只按实际可比条件报告，未测则不宣称。

**阶段出口：** 完整自动证据包可供人工审核；未达门槛则定位并修复，建立新 RC 后按协议重跑。

## 阶段 6：独立干净 Windows 的无 Java 验收（P0，外部环境就绪后约 1—2 工作日）

**涉及：** `docs/clean-windows-acceptance.md`、发行包及独立机脱敏报告。用户先前表示可提供测试环境；收到环境信息后执行，不把等待时间算作通过。

- [ ] 记录系统、Python 3.12+、依赖、CPU/内存、浏览器与网络条件；确认没有可供 MUSE 使用的 Java/Javac/Gradle。用阶段 4 的同一 wheel 全新安装，不复制开发机虚拟环境。
- [ ] 测中文和空格路径、API/Worker/网页/终端、后台重启/恢复、取消进程树、审批、工作树、三类真实任务及成果下载。测试失败要能诊断与恢复，不能静默成功。
- [ ] **真实创建文件符号链接**，与 `..`、绝对路径、junction 一起验证外部哨兵读写被拒绝，合法工作区操作仍成功；WinError 1314 或跳过不计通过。
- [ ] 在独立机执行发行范围工程检查与同一候选的正式业务协议；如果条件和阶段 5 不同，另开独立结果记录，不拼接成绩。做数据备份/恢复/回滚演练，核对原项目和数据哈希。

**阶段出口：** 证明无 JVM 安装与运行、必测项零失败零阻塞、真实符号链接边界通过，且恢复和回滚可重复。

## 阶段 7：最后进行人工审核与发布判定（P0，约 1—2 工作日）

**涉及：** `docs/manual-benchmark-handoff.md`、`docs/release-acceptance.md`、`docs/java-migration-matrix.csv`、`README.md`、最终成果与哈希清单。

- [ ] 开发与自动验证稳定后，将完整 60 次结果交给用户审核事实、引用、文档/代码成果、风险操作；第二位独立人工评审复核文本通过项和争议项，记录分歧与判定依据。
- [ ] 按 G1—G8、原多 Agent/长上下文/MCP 指标、无 Java 干净机、权限契约与迁移/回滚逐项签结论。任何 BLOCKED、NOT_RUN、关键断言失败或版本不一致均不得写“验收通过”。
- [ ] 确认源项目主许可证与第三方分发条件；生成同一源码提交对应的 wheel、源码 ZIP、SHA-256、安装/升级/回滚说明、已知限制与三类演示成果。许可证未确认时仅本地交付。
- [ ] 若人工审核指出产品缺陷，修复后重新冻结候选并重跑受影响工程检查和完整正式批次；最终文档明确写 **PASS** 或 **NOT_ACCEPTED**，不以建议性话术替代结论。

**阶段出口：** 人工与自动证据指向同一最终包，G1—G8 全部满足，方可宣布“Java 运行时完全替代版已验收”。

## 建议顺序与预计投入

关键路径：**阶段 1 → 2 → 3 → 4 → 5；阶段 6 在独立环境到位后执行；阶段 7 最后执行。** 阶段 5 与 6 可在同一冻结候选上并行准备证据，但二者的结果须各自完整。当前最值得先做的是修复多 Agent 的 checkout/numeric 整合失败，因为它是已有证据确认的产品问题。长上下文与 MCP 则需在服务恢复后补全同候选真实调用。用户只需在最后提供独立 Windows 环境与参与人工评分；此前开发与自动检查可继续推进。

按现有代码基础估计工程与自动验证约 **5—11 个工作日**，独立机与人工审核再约 **2—4 个工作日**；等待环境、服务故障、模型费用额度或新缺陷不计入这个估计。这是排期参考，不是无条件交付日期。8 小时耐久、完整 RSS、单/多 Agent 加速比若要作为宣传指标，另开有方法和对照条件的性能试验；未完成前从验收声明中排除。
