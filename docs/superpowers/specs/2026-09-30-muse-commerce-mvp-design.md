# MUSE 独立站商家团队首版设计规格

版本：1.2｜2026-10-01（Australia/Sydney）｜状态：开发中的设计基线；完整业务闭环尚未验收。本版补充显式页面初始化与真实功能测试边界。

## 1. 已确认目标

用户已确认首版平台为 **WordPress + WooCommerce**。MUSE 面向个人与小团队独立站商家，以电商网站开发为应用入口，随后帮助商家完成商品上新及持续改进。首版做通“建站”和“新品上线”，团队只设置店长、网站开发、商品内容三个业务角色；营销和分析 Agent 在真实使用后扩展。

Coding Agent 作为网站开发执行能力持续参与业务任务，也保留不依赖店铺的独立编程入口。MUSE Agent Runtime 继续采用 Python；WordPress 及其插件使用 PHP 是平台运行要求，不是恢复 Java 或重写 MUSE 为 PHP。

### 1.1 开发接口补充（2026-10-01）

原 P3 七类固定操作扩为八类：增加 `create_owned_page`，其 payload 仅含 `slug,title,content,template`。slug 只允许 1–64 字符的小写 ASCII 字母/数字/连字符；标题和正文为有上限的纯文本；模板仅允许自有 page/page-cart/page-checkout/page-about/page-contact。资源为 `page-slug:<SHA256(slug)>`，必须以固定只读资源查询证明不存在；创建 draft 并标记当前项目所有权，重复操作回原持久回执。已有同 slug 页面拒绝，不自动接管或覆盖。主题安装不得隐式创建页面或修改商店选项。

SKU 不存在证明为固定 `GET /wp-json/muse/v1/resources?sku=...`；页面 slug 证明为同一路由 `?page_slug=...`，仅允许其中一种。返回具体规范化资源状态和 SHA-256，Python 端重新计算且严格校验，不凭有上限的快照推断不存在。远端在持久回执/事务内再次查询，禁止将早先只读结果视为写授权。

主题资源指纹同时包括有效 DB 模板、样式、固定 15 文件 SHA-256 与自有导航。设置指纹包括首页、商店、购物车、结账 ID。导航更新必须绑定主题和每个引用页面的版本，仅覆盖自有导航/header，不覆盖商家的其他模板。已生成的物理页面 ID 与跨操作依赖变更仍须由 P7 的可信编排绑定，不能自动替换已批准操作/指纹来绕过审查。

Windows 便携 WordPress 可用于真实 CMS 功能与故障验证；它不替代 Linux 执行隔离、连接器身份、镜像兼容和越权探针。版本清单在这些证据完成前保持未验证；P6/P7 的公开自动发布门槛保持关闭。

## 3. 首版交付范围

| 项目 | 明确边界 |
|---|---|
| 使用形态 | 单商家、本地 MUSE 工作台；一个逻辑店铺项目，staging/live 各一个独立 WordPress 实例 |
| 建站方案 | 自有 `muse-storefront` 原生区块主题 + WordPress Site Editor + WooCommerce 原生购物车/结账；MUSE 不重做拖拽编辑器 |
| 托管目标 | 首版只验证 Linux Docker Compose 部署；Windows 可运行 MUSE UI/API，但编程隔离和站点部署由 Linux 主机承担 |
| 页面 | 首页、商城列表、商品详情、购物车、结账、关于、联系；政策页面内容由商家提供，未提供不得生成虚假的政策 |
| 业务 | 单语言、单币种、实体简单商品；每批最多 20 件；不含变体、订阅、多仓、跨市场税务或复杂促销 |
| 图片 | 商家上传 PNG/JPEG/WebP；每文件最多 10 MiB、每商品最多 5 张；不抓取任意远程图片，不生成虚构商品实拍 |
| 首版编辑 | 对话修改自有主题的 templates/parts HTML、CSS、theme.json 和结构化页面内容；保留原生编辑器入口 |
| 代码发布 | 只发布静态区块主题变更和固定产品代码；Agent 生成的 PHP、任意 JS、依赖安装和任意插件不纳入自动发布 |
| 交易 | 复用 WooCommerce；自动验收使用离线测试付款方式，真实付款、税费与运输配置上线前由商家确认 |
| 正式平台 | 公共多商家 SaaS、计费、自动投放、客服退款、全平台迁移均不计入首版 |

限制自动发布代码类型，是首版可验证范围，不削弱直接编程入口可处理 Python/PHP/JS 等项目的能力。首版主题采用允许列表中的原生 WordPress/WooCommerce 区块，不声称任意主题和插件均兼容。

WordPress/WooCommerce/PHP/数据库镜像版本在第一阶段选择相互兼容的受支持发行版，写入锁定清单及镜像 digest；未完成真实兼容验证前不以 `latest` 代替支持版本。

## 4. 两条完整流程

### A：建站

输入品牌、商品资料、风格、语言、币种 → 店长形成结构化需求 → 商家确认页面结构和风格 → 商品内容 Agent 提交可核对文案/商品草稿 → 网站开发 Agent 实现自有主题 → 在 staging 配置页面与商品 → 截图、移动端及购买流程验证 → 商家审查 ChangeSet → 发布到准备好的 live 实例 → 回读核对并保存发布回执。

本地 staging 实例可按锁定 Compose 配置创建；live 实例按运维指南预先准备并连接。第一版不购买域名、自动创建云账户或建设通用托管平台。未连接 live 时最多完成 staging 验收，状态为等待上线环境。

### B：新品上线

上传结构化 CSV 和图片 → 校验 SKU、价格、库存、币种及缺失字段 → 店长协调内容与页面任务 → 商品内容 Agent 基于原始事实生成标题、描述和分类建议 → 开发 Agent 按需修改新品页面区块 → staging 建立草稿并预览 → 商家确认逐件商品与页面差异 → live 先写入 draft → 回读验证 → 发布商品/页面 → 展示成功、部分成功或待对账清单。

SKU 既有商品默认视为冲突，首版不自动覆盖；同一次任务的已记录回执可幂等恢复。描述不允许创造输入中不存在的材质、认证、功效或价格。20 件以上拆批前需要商家确认。20 件是产品限制，与平台 batch 上限无关。

## 5. 三角色协作

| 角色 ID | 输入与产出 | 能力限制 |
|---|---|---|
| `store_manager` 店长 | 需求、店铺快照 → 带依赖的计划、分工、成果汇总 | 可规划/委派/提请审查；不能运行 Shell、直接写生产店铺或代替商家批准 |
| `site_developer` 网站开发 | 结构化 Brief、页面方案、隔离代码工程 → 代码 revision、构建产物、测试报告 | 可在授权工程读写代码和执行验证；只访问 staging；不获得 live Token、发布器身份或宿主 Docker socket |
| `product_content` 商品内容 | 商家输入和脱敏目录 → ProductDraft、文案、事实缺口 | 无 Shell、生产写入或自主价格/库存决策；只能提交结构化草稿 |

复用现有子任务、共享预算、角色来源快照和团队看板；不新增第二套 Agent Loop。代码和内容使用不同成果区；店长汇总时绑定每份成果的哈希和来源。依赖已完成才允许后续步骤开始；根任务取消后不能继续委派、发起新的发布操作或自动重试。取消前已经发出的远端操作可能仍完成，必须保留回执并对账，不能宣称取消已撤回远端变更。

确定性验证服务不是第四个业务 Agent。保留原内置 verification 角色用于已有编程场景；Commerce 发布以验证服务的可核对回执为准。

## 6. 架构及边界

```text
商家工作台 / 直接编程入口
          │
Commerce 项目 API、工作流、店长及结构化成果
          │                     │
现有 Python Runtime        专用发布服务（不对模型暴露）
任务、Worker、子任务        版本校验、审批、幂等、对账
代码工作区、验证              │
          │              WordPress Connector Plugin
隔离 Linux 执行与 staging     │
                       WooCommerce / 原生区块主题
```

新增 Commerce 项目与现有 Task 分开建模，通过 task ID 关联；不改变 `scenario='coding'` 的已有含义。店铺连接、品牌资料、快照、业务计划、成果、审批及发布回执使用项目 ID 和版本，不能只保存在模型上下文。

现有 `main.py` 保留本地身份边界并挂载 Commerce Router，不直接向公网开放。预览采用独立 URL 新窗口，避免放宽现有 `frame-ancestors 'none'`；WordPress editor 也通过显式入口打开。

连接器部署为单独 Python 服务；生产凭据只在连接器秘密存储中存在。Agent 执行环境不能读取其目录、环境或 Docker socket，不能访问 live/连接器服务；连接器 API 不接受模型提供的任意 URL 或原始 Shell。允许写入的操作类型、环境、资源范围、版本和批准摘要由后端验证。

自有固定 WordPress Connector Plugin 提供只读能力查询、快照、有限页面/商品操作、预览映射、版本比较和持久回执；它由产品开发者维护，Agent 不生成/改写插件。原生 API 可处理商品等基础操作，但不假设原生接口已经提供 MUSE 的幂等、版本审批和主题部署契约。

## 7. 发布与失败语义

- 一次商家发布批准绑定：project/store/environment、ChangeSet SHA-256、代码与内容哈希、触及资源的预期版本、验证报告哈希；有效期 30 分钟。
- staging 项目操作需显式授权且绑定 staging 实例；此授权不能转换为 live 批准，也不绕过 Runtime 工具权限。
- 代码、内容、目标资源或店铺设置改变后，旧预览/验证/审批为 STALE。新订单写入不使不相关页面审批无故失效；只能比较实际触及资源及必要结账配置。
- 数据库、库存、订单和支付记录不以 staging 整库覆盖 live。发布仅更新明确资源；所有新商品先 draft；回执逐项记录。
- 多步发布不声称跨 WordPress/WooCommerce 操作原子性。失败返回 PARTIAL；超时返回 NEEDS_RECONCILIATION，先按持久 operation_id 对账，不盲重发。
- 回退只恢复本次触及且未被他人再次修改的资源；不得覆盖订单或已售商品的库存。回退自身是新 ChangeSet，需批准。
- 工具执行成功、模型回复“完成”、staging 截图均不能单独证明 live 发布成功。

### 7.1 统一错误分类、恢复与测试归属

业务 API 错误使用 `code, message, field_errors, retryable, next_action, project_id, plan_id, operation_id`；关联 ID 仅在已创建时返回。公开信息脱敏，不返回 Token、原始鉴权头、内部文件路径或未脱敏的服务错误。`retryable` 只表示允许的后续动作，客户端不得据此透明重发写入。

| 错误码 / 触发条件 | 状态与行为 | 恢复办法 | 测试归属 |
|---|---|---|---|
| INPUT_INVALID：CSV/图片不合规、超过 20 件、币种错误 | HTTP 422；逐行/逐字段错误，不创建可发布计划、不写店铺 | 商家修正并重新提交 | P5/P8/P9 |
| FACTS_INCOMPLETE：商品事实、政策或必要设置缺失 | 已有计划为 NEEDS_INPUT；只保存草稿 | 补充原始事实或商家明确确认；不由模型编造 | P4/P5/P8 |
| AUTH_REQUIRED / PERMISSION_DENIED：连接凭据失效或权限不足 | 对远端问题返回脱敏业务码，计划 BLOCKED；本地 API 无效身份仍为 401/403 | 重连或修正权限；不自动提高权限 | P2/P3 |
| UNSUPPORTED_CAPABILITY：版本不兼容、变体商品或非支持主题/区块 | 校验请求返回 422；已有计划 BLOCKED；发布为零写入 | 修改需求或部署受支持环境 | P0/P2/P5 |
| RESOURCE_CONFLICT / REVIEW_STALE：手工修改、版本或哈希变化 | HTTP 409；计划 STALE，旧批准无效 | 刷新快照、合并商家改动、重新预览/验证/批准 | P2/P5/P6/P7 |
| APPROVAL_REQUIRED / APPROVAL_EXPIRED：无有效业务批准 | HTTP 409；尚未开始时保持 REVIEW_REQUIRED，零发布操作 | 新批准；不接受模型或技术工具批准替代 | P7/P9 |
| READ_TEMPORARY_FAILURE：只读连接超时、429/5xx | 允许最多 2 次额外只读重试；失败后 BLOCKED，成果不得标已验证 | 恢复服务后显式继续 | P2 |
| MODEL_UNAVAILABLE / BUDGET_EXHAUSTED：服务不可用、配额或根预算耗尽 | 服务/配额问题 BLOCKED；根预算耗尽 FAILED；保留检查点与子任务结果 | 修复服务或商家明确调整预算后继续；不切模型/密钥或新建根任务逃逸预算 | P4/P10 |
| MODEL_OUTPUT_INVALID：结构化产物不符合 schema | 预算内最多 1 次产物修正；仍无效为 FAILED；没有可发布成果 | 显示缺失字段/事实证据，修正需求或成果 | P4/P8 |
| VERIFICATION_FAILED / VERIFICATION_UNAVAILABLE：行为测试失败或工具/环境缺失 | 报告 FAIL/BLOCKED；计划 FAILED/BLOCKED；禁止发布 | 修复并对新 revision 重验 | P6/P7 |
| WRITE_OUTCOME_UNKNOWN：写入发出后超时、断线或执行进程丢失 | 业务响应保留 receipt 和 NEEDS_RECONCILIATION；不透明重发，不伪造失败回滚 | 按 operation_id 读远端回执；找不到确定结果则继续阻止后续写入 | P3/P7/P10 |
| PARTIAL_APPLY：有操作成功，其他操作确定失败 | 状态 PARTIAL；逐项展示真实回执，停止后续写入 | 刷新快照，针对剩余操作或可回退资源创建新 ChangeSet，并重新批准 | P7/P8 |
| EXECUTION_BOUNDARY_UNAVAILABLE：缺 Linux 隔离或越权探针失败 | BLOCKED；关闭该 Commerce CODE 发布路径 | 修复执行环境并重跑探针；不放宽生产权限 | P6 |
| CANCELLED_WITH_INFLIGHT：取消时远端操作已发出 | 禁止新增步骤；不确定写入先 NEEDS_RECONCILIATION；已成功的写入记录 PARTIAL，不显示撤销成功 | 完成只读对账；取消不自动回退，回退需新批准 | P4/P7/P10 |

只读重试的等待依次为 1 秒、2 秒；若有合法 Retry-After 则遵守，但单次等待超过 60 秒或超出根任务剩余预算时暂停自动重试并提示稍后继续。重试均计入已有工具/时间预算。模型服务错误不自动重复付费请求；一次产物修正仍计入根模型预算。所有写操作禁用 HTTP 客户端透明重试，必须走操作回执协议。

已有计划的详细错误在项目事件和检查点中持久保存。失败不覆盖以前成功回执；恢复记录 attempt 编号、前后 revision 和恢复原因。环境/授权等 BLOCKED 与产品缺陷 FAILED 分开报告。

## 8. 验收要求

| 编号 | 必须提供的证据 |
|---|---|
| AC01 原能力 | 未配置 WordPress 时，直接编程、研究、资料、MCP、已有子任务、恢复/取消与旧 API 回归可用 |
| AC02 建站 | 5 商品 fixture 生成 7 类页面，在 390/768/1440 px 宽度检查核心页面；完成测试订单；后台显示验证和版本 |
| AC03 新品 | 5 件新品输入 → 草稿 → 审查 → 发布 → API 和页面回读；重复提交产品数仍为 5；批量超过 20 拒绝 |
| AC04 上下文 | 后续任务复用已确认风格和商品事实；手动改价/改页面后重新快照并拒绝旧批准；不导入订单客户 PII |
| AC05 团队 | 店长真实创建开发与内容子任务，消费两方成果；取消/重启/预算上限不重复创建资源、不绕过审批 |
| AC06 生产边界 | 未批准 live 写入数为 0；被撤销/过期/旧版本批准不能发布；Coding 越权读凭据/访问 live 实测失败 |
| AC07 故障 | 超时、断网、部分成功、WP 手动编辑、已新增订单、SKU 冲突和页面修改冲突各有真实或故障注入证据 |
| AC08 可迁移 | 主题包、商品/页面导出、部署说明在第二套相同版本空白环境恢复，并重新验证；不自动包含秘密和订单 |
| AC09 质量 | 商品事实缺失明确标记；不虚构商品属性/政策；商家能从审查页定位差异并取消；手动编辑保留冲突证据 |

真实模型验收每条流程 3 个预先冻结案例；逐例记录版本、输入、人工干预、结果、Token 与费用（费用不可得则 unknown）。目标为 6/6 完成或明确恢复到完成，任何失败都保留，不用后续重试覆盖首次结果。发布边界故障探针必须全部通过。指标是本首版拟定验收门槛，不代表当前成绩，不复用旧 SWE/MCP 分数。

## 9. 后续扩展条件

先收集至少 10 次真实商家任务的人工反馈与执行记录；定位最高频未满足需求，再增加营销 Agent。接入经授权的真实经营数据后增加分析 Agent；报告须能追溯到数据，执行动作仍走同一审批/发布服务。角色扩展复用任务契约和工具范围，不通过角色提示词取得额外权限。

## 10. 官方技术依据（2026-09-30 查询）

- [WordPress Application Passwords](https://developer.wordpress.org/rest-api/using-the-rest-api/authentication/)：生产远程调用采用 HTTPS，并按账户 capability 授权。
- [自定义 REST 端点](https://developer.wordpress.org/rest-api/extending-the-rest-api/adding-custom-endpoints/)：固定 Connector 接口必须提供权限校验。
- [区块主题模板](https://developer.wordpress.org/themes/core-concepts/templates/) 与 [theme.json](https://developer.wordpress.org/themes/global-settings-and-styles/introduction-to-theme-json/)：建站基于原生模板和样式模型。
- [WooCommerce REST API](https://developer.woocommerce.com/docs/apis/rest-api/)：商品管理接口；具体调用在锁定版本集成测试中验证。

上述官方能力是技术选型依据，不表示 MUSE 已连接或通过实际店铺验收。

## 11. 分阶段实现与自检放行

实现按配套计划的 P0–P10 逐项进行，每项必须有：前置依赖检查 → 可复现的失败测试 → 实现 → 相关回归 → 边界/故障检查 → 脱敏证据 → 自检结果。存在必需失败或环境阻塞时，依赖该能力的任务不得放行；无依赖的离线任务可以继续。产品代码、任务完成和正式验收是不同状态。

| 交付阶段 | 任务范围 | 必须检查的成功和错误路径 | 阶段放行成果 |
|---|---|---|---|
| 第一阶段：项目、连接和团队 | P0–P4 | 旧功能兼容；迁移可恢复；只读上下文准确；凭据不可见；越权写入被拒绝；重复请求/重启不重建角色子任务 | 一个项目、一套实际兼容版本、只读店铺快照、三角色任务轨迹及固定操作回执合同；不宣称建站已完成 |
| 第二阶段：建站、验证和发布 | P5–P7，依赖第一阶段接口与安全证据 | 7 类页面和测试购买流程；代码修改使旧验证失效；未批准/冲突/超时/取消边界；live-test 的写入与回读一致 | 从需求到建站预览、审查、批准、live-test 发布的完整演示；未知结果可对账，手工编辑和订单不丢失 |
| 第三阶段：新品、工作台和验收 | P8–P10，依赖第二阶段发布内核 | 输入错误、商品事实缺口、SKU 冲突；5 件新品重复提交不重复；原入口可用；6 个真实模型案例及人工检查 | 两条完整流程、独立环境回归、迁移导出与 AC01–AC09 最终证据矩阵；必需门槛全部满足才称首版验收 |

每个阶段输出 `docs/commerce/checkpoints/stage-N.md` 与脱敏证据目录。报告记录：source commit/文件哈希、环境锁定清单、完成任务、检查命令、预期与实际结果、首次失败与修复、失败/跳过/阻塞、原编程回归、各证据路径和下一阶段决定。所有报告初始 NOT_RUN；不得预填 PASS。

若第一阶段只完成 mock，阶段结论是离线合同完成、真实平台 BLOCKED；可以开发第二阶段的离线模板与 UI，但不能把真实发布或安全隔离标为通过。每阶段自检由实施者执行并记录，最终商家人工验收和独立环境测试另行保留，不相互替代。
