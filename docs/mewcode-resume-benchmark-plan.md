# Mewcode Python 版项目介绍 Benchmark 测试计划

状态：**计划，尚未按本计划完成测试**。适用对象为当前 Python 核心的 MUSE/Mewcode 候选版本；本计划检验项目介绍中的能力和量化表述，不把历史 StarCode、其他模型或其他提交的结果自动算作本版本成绩。

## 1. 要回答的问题

| 项目介绍中的表述 | 对应试验 | 可以对外采用该表述的条件 |
| --- | --- | --- |
| 基于 ReAct 的编程 Agent；MCP、Skill、多 Agent 可用 | F：功能与协议；S：真实修复 | 运行轨迹、扩展调用和最终补丁均可复核；S 的修复率须标明数据集版本和分母 |
| JSONL 跨会话记忆、LLM 自动提取、项目指令分级加载 | J：记忆与指令 | 按实际运行入口验证持久化格式、提取质量、作用域与优先级；实现不同则如实改写介绍 |
| MCP 百级工具描述 Token 减少 85% | M：同目录 FULL/LAZY 配对 | 预先定义的描述 Token 口径下降 ≥85%，工具选择质量不下降；注明仅是描述 Token，不是总费用 |
| 两层压缩支持 8 小时以上会话且关键事实不丢 | C：配对事实保留；C8：耐久 | 同一事实夹具复现前后 17%→100%；另有至少 3 次超过 8 小时的实跑，关键事实、恢复与副作用检查全过 |
| 单次会话权限弹窗平均约 30 次降至 5 次以内 | P：同任务脚本的旧/新策略配对 | 平均**实际展示给用户**的确认次数：旧版约 30，新版 ≤5；安全哨兵全部通过 |
| 可选 OS 级沙箱、内核级隔离 | X：隔离边界验证 | 只在对应操作系统、具体沙箱后端及攻击夹具均通过时作限定表述；应用路径策略不能替代此试验 |
| 信息保留率从 17% 提升到 100% | C：冻结事实集配对 | 相同事实、同一模型和判分器，旧/新实现各运行；按预注册分母计算，逐项证据可查 |
| 多 Agent 跨文件重构耗时降低约 60% | A：单/多 Agent 配对 | 相同任务、模型、质量门槛下，配对墙钟耗时的聚合降幅达到约 60%，同时披露 Token 与费用变化 |

“五层分层架构”“独立负责”“借助 Claude Code”属于设计和贡献归属，不能由性能 Benchmark 证明；另以架构图、提交记录和设计决策记录核对。上述数字均是**待验证目标**，不是当前测试结果。

## 2. 冻结、对照与证据规则

1. 正式测试前冻结源码 commit、依赖锁、基准脚本与夹具哈希、模型 ID/版本、系统提示和 Skill、MCP 目录、压缩阈值、权限策略、操作系统及沙箱能力。保存 `manifest.json`；每组试验只改变所声明的自变量。模型、提示或候选代码变化后重新成组运行，不拼接最好成绩。
2. 每次任务使用独立工作区、状态库和缓存。记录开始/结束单调时钟、请求及工具轨迹、输入/输出/缓存 Token、审批 UI 事件、退出码、补丁和测试日志。真实密钥、私人文档及完整敏感请求不得写入可公开证据。正式运行前为各组设 API 请求、Token、工具调用、时间和费用停止上限；触顶按 FAIL/预算耗尽记录，不临时放宽。
3. `PASS` 需预注册断言和原始证据齐全；`FAIL` 包括超时、预算耗尽、质量不达标或证据缺失；`BLOCKED` 仅用于确实缺少环境前提；`NOT_RUN` 不参加成功数但保留在计划分母。报告同时给出四类数量，不能把 BLOCKED 排除后写作“100%”。
4. 随机化配对顺序，锁定相同 API 服务、模型参数、网络和并发上限；报告中位数、均值、p95、每任务配对差和 95% bootstrap 区间。区间仅描述这批任务的不确定性，不能外推所有真实项目。
5. 试验前先做 3–5 个不计正式成绩的冒烟任务。正式集冻结后不得据结果修改提示、夹具或阈值；如修复产品缺陷，升新候选并完整重跑受影响的正式组。

建议证据目录：`work/resume-benchmark/<candidate-id>/<group>/<case-id>/<run-id>/`；最终导出脱敏 `summary.json`、逐例 `cases.csv`、`manifest.json` 和证据哈希清单。旧证据保留原路径与结果，不重写。

## 3. F：功能与安全基线

先完成现有 20 场景 ×3 轮的 MUSE-Bench，覆盖编程、研究、文档、后台恢复、权限与记忆。按原标准逐项人工审查，并在可创建真实文件符号链接的独立 Windows 环境跑 P01；未通过时不得宣布 Python 完全替代 Java。另用固定轨迹核对 ReAct 的“模型决定→工具执行→观察结果→继续/停止”、MCP 搜索/加载/调用、Skill 指令加载与作用域、多 Agent 子任务提交及主 Agent 整合。轨迹中的工具调用和最终产物都必须真实存在；仅有模块或模拟接口不算功能通过。对“五层安全隔离”逐层列出实施位置、保护边界、可绕过路径和对应拒绝测试；无法列出并验证五个独立层次时，不使用该数量表述。

这是产品验收基线，不替代下面针对简历数字的专项实验。当前 RC8 本机 60 次中 57 次仅为自动预筛待人工审核、3 次 P01 因环境阻塞，不能记作本计划的正式 PASS。

## 4. J：跨会话记忆与项目指令

准备 60 条带真值的合成会话片段：20 条应提取稳定偏好或项目约束、20 条一次性任务信息不应提取、20 条包含更新/冲突/虚构密钥；由两名评审预先标注。使用同一模型运行自动记忆提取，报告精确率、召回率、误存敏感信息次数和冲突处理正确率；目标为敏感信息误存 0、跨项目泄漏 0，其余质量指标报告实测值，不凭单例宣布可用。另测试写入→关闭→重开→新会话召回、损坏末行、并发追加、删除后不再注入，以及用户级/项目级/目录级指令的优先级与冲突；每项保留磁盘内容、请求投影和前后哈希。

必须分别运行旧 `mewcode` 入口与当前 `muse` 入口，并记录哪个入口真正使用 JSONL、哪个使用 SQLite 或其他持久化格式。当前 Python 统一运行时的权威会话状态已改用 SQLite 事件/检查点；若项目介绍指向当前 MUSE，就不能把旧私有运行函数的 JSONL 能力直接算给它。功能成立但存储格式不同，应把简历文字改为“持久化跨会话记忆”，不要保留“JSONL”这个未经当前入口验证的限定词。

## 5. S：SWE-bench-Live 真实修复能力

- 使用官方 Python 数据集的一个**明确冻结快照与 split**，保存数据集 revision、抽样脚本和实例 ID。先用不少于 20 例做流水线先导；正式样本建议至少 100 例，按仓库和难度分层后固定随机种子抽取。若预算不足，报告实际样本数，不能把先导集当正式集。
- 按[官方评测协议](https://github.com/microsoft/SWE-bench-Live/blob/main/evaluation/README.md)：Agent rollout 只能见 `problem_statement` 和实例镜像，不能见 `patch`、`test_patch`、`FAIL_TO_PASS`、提示字段或官方评测结果；禁止在 rollout 中查询公开答案、提交或评测服务，模型 API 通道单独放行。每个实例、每个配置只做一次正式 rollout。保存完整轨迹和 `git diff`，由独立评测进程在 rollout 后评分。
- 按官方建议在本机用 gold patch 重复验证 3 次，冻结有效实例集合；同时公布原抽样数、环境无效数和有效分母，不能静默剔除失败实例。正式指标为 `resolved = 官方评测通过数 / 有效实例数`，附 Wilson 95% 区间、每例耗时、Token、估算 API 费用和失败类型。通过率没有预设的“宣传目标”；简历写实际数值及条件。
- 可选同模型、同预算的单 Agent 基线配对，用于识别框架影响。外部排行榜分数不得直接当成当前 Mewcode 的成绩。

## 6. M：MCP 延迟加载与 Token

准备冻结的 100 工具目录（可另加 200 工具压力组）、30 个需要不同工具的任务和干扰工具。FULL 在每次模型请求中提供全部目录定义；LAZY 使用生产环境的 `discover → search → load → call`，保持同一模型、工具描述、目标答案、预算与任务顺序。每个任务两组各运行 3 次，共至少 90 个配对；记录远程调用是否选对工具和参数。

分别报告三项，不相互代替：

```text
初始描述降幅 = 1 - LAZY 首次请求中工具定义 Token / FULL 首次请求中工具定义 Token
会话描述降幅 = 1 - LAZY 全会话工具定义及目录索引 Token / FULL 全会话对应 Token
实际输入降幅 = 1 - LAZY API 输入 Token 总量 / FULL API 输入 Token 总量
```

使用相同 tokenizer、JSON 序列化、消息边界和缓存记账方式；目录索引、搜索结果及已加载 schema 计入会话描述。标题中的“工具描述 Token 减少 85%”仅在**会话描述降幅 ≥85%**、目标工具/参数正确率不低于 FULL 且无越权调用时采用；若只有初始降幅达标，则只能写“初始工具定义 Token 减少 X%”。总 API 成本另按实际账单或定价和用量计算，不等同 Token 降幅。

已有 RC8 配对试验的累计 schema Token 为 FULL 443,230、LAZY 134,778，约下降 69.6%；实际输入为 341,936 对 220,595，约下降 35.5%。这组证据**不支持**当前 Python 版“85% 会话描述降幅”的说法；正式 M 组仍需按上述统一口径重跑。

## 7. C / C8：事实保留与 8 小时以上耐久

**C：前后配对。** 从旧版历史材料取得可运行的“修复前”提交或镜像；与“修复后”使用同一模型、事实集、日志长度、检查点及判分器。冻结至少 100 个原子事实，含早期事实、更新值、相互冲突的旧值、来源和待办状态；在 100K/200K/300K 累计输入及进程重启后盲问。每个事实只按预注册标准判一次：`事实保留率 = 正确且有来源的事实数 / 预注册事实总数`。旧版约 17%、新版 100% 必须是**同一固定分母**上的实测，附逐项错漏；若找不到可运行的旧版，仅报告新版绝对表现，不写“17%→100%”。

**C8：真实时间耐久。** 至少 3 个相互独立、各持续 **8 小时 15 分钟以上**的连续编程会话；每 30 分钟注入新事实与代码任务、问回早期和最新事实，并触发压缩、历史检索、关闭/重开界面及一次 Worker 重启。每轮预注册 ≥40 个关键事实检查点；要求全部正确、来源一致、已完成工具动作不重放、代码验证记录真实、任务可继续。记录墙钟连续时长、模型可用性、活动时间、压缩次数、状态库大小、峰值 RSS、Token 和费用。模型服务中断记清楚，不能把暂停时间充作 8 小时连续运行。100K/200K/300K 的短时压力测试不能代替 C8。

## 8. P / X：审批体验与隔离

**P：同一动作脚本对照。** 准备至少 30 个代表性会话，覆盖读文件、编辑、测试、包安装、网络、越界及高风险命令。用原 30 次左右的历史策略与新策略分别回放相同脚本；自动批准预定的低风险请求、拒绝高风险请求。计数来源必须是前端实际展示的确认事件，单纯数据库审批行另列。主指标 `平均每会话弹窗数 = 展示弹窗总数 / 预注册会话总数`；同时给中位数、p95、未完成数及每类动作分布，未完成会话不能以低弹窗数冒充体验改善。只有旧版实测约 30、新版平均 ≤5，且同一脚本的任务完成率不下降，才保留“30→5 次以内”。若旧版环境不可复现，不能写有对照的降幅。

安全门槛独立计分：越界读写、符号链接/junction、参数变更、过期/重复批准、诱导指令、跨任务授权复用均不得发生未授权执行或泄露；50/50 风险探针“被用户拒绝”不能充当系统自动识别全部风险。当前 Python 权限回放的确认**中位数为 9**，与“平均 <5”既不同指标也尚未达成该宣传结论。

**X：可选 OS 沙箱。** 分别在明确启用/关闭的配置下用独立进程及工作区外哨兵验证文件、进程和网络边界，并记录 OS 版本、沙箱后端、内核机制和实际拦截证据。没有实现或无独立攻击测试时，项目介绍只能说“计划支持/可接入”，不能声称已有“内核级隔离”或“安全全自动模式”。

## 9. A：多 Agent 加速

冻结至少 12 个确有可拆分子任务的跨文件重构任务，另设 4 个串行依赖任务作为负面对照；每项用单 Agent 与双子 Agent+主 Agent 整合各跑 3 次，随机化先后顺序。两组保持相同模型、仓库基线、测试命令、总 Token/工具/时间上限；多 Agent 允许并发，但记录累计请求数、峰值并发和成本。主 Agent 必须实际检查子提交、合并并统一运行测试；不能把两个子 Agent 的草稿各自完成当作任务成功。

```text
单任务降幅 = 1 - 多 Agent 成功完成的墙钟秒数 / 单 Agent 成功完成的墙钟秒数
总体降幅 = 1 - 配对任务多 Agent 墙钟时间之和 / 配对任务单 Agent 墙钟时间之和
```

只在双方均满足相同隐藏测试、变更范围和代码审查门槛的配对任务上计算速度；失败、超时和额外人工介入另列，不能为了提高速度比而删除。报告总体降幅、每任务分布和 bootstrap 区间；“约 60%”须预先定义为总体降幅至少 55%、点估计接近 60%，且质量不下降。12 项 ×3 轮仍是有限样本，须写明任务集，不外推所有跨文件重构。已有 checkout/numeric/text 3/3 仅证明协作流程可运行，不证明 60% 加速。

## 10. 执行顺序与放行

| 阶段 | 工作 | 完成物 |
| --- | --- | --- |
| 0 | 冻结候选、夹具、环境和口径；跑小规模冒烟；核对可用预算与独立 Windows 环境 | manifest、实例清单、预算上限 |
| 1 | F、J、P、M：功能/记忆/安全与配对 Token，修正测量器但不调正式集 | 逐例轨迹、记忆评分、审批 UI 计数、Token 明细 |
| 2 | S、A：SWE-bench-Live 正式修复与单/多 Agent 对照 | 官方评测日志、补丁、配对速度表 |
| 3 | C、C8、X：事实前后对照、8 小时耐久、OS 隔离 | 事实评分表、三次完整时间轴、隔离证据 |
| 4 | 独立复核文本/争议项、汇总置信区间、审计脱敏与声明 | 可公开报告与“不支持的表述”清单 |

仅 C8 的三次串行耐久运行就至少需要 24 小时 45 分钟，尚不含环境准备、SWE-bench-Live 镜像/评测、人工复核和故障返工；可在资源隔离的机器上并行，但不得让资源竞争改变配对条件。正式费用取决于当时模型价格和实际用量，不在未测前承诺金额。

发布报告逐条标 `VERIFIED / NOT_VERIFIED / BLOCKED / NOT_RUN`，引用对应证据和具体版本。简历只采用 `VERIFIED` 的数字；未达到时改写为已测到的实际数值或不带数字的能力描述。现有 MUSE 发布门槛仍独立适用：独立 Windows P01、人工基准审核及许可证核实未完成前，不宣称 Java 完全替代版正式验收通过。
