# 多协议 LLM 终端对话客户端 Spec

## 文档状态

- 功能编号：001
- 状态：IMPLEMENTED（当前回归测试通过；真实 Provider E2E 证据单独记录）
- 所属项目：Star Code AI Coding Agent
- 本期定位：Star Code 的第一块纵向基石
- 后续文档：`plan.md` → `task.md` → `checklist.md`

## 背景

Star Code 是一个从零构建的、Claude Code 风格的终端 AI Coding Agent。本功能是其第一块基石：在尚未加入工具调用、权限、记忆和代码修改能力之前，先打通“用户 ↔ LLM”的最小闭环，让用户能够在终端中与大模型进行流畅、可恢复的多轮对话。

本功能优先验证四项基础能力：

1. 多模型协议适配。
2. 流式事件处理。
3. 单会话上下文管理。
4. 非阻塞终端交互。

后续文件工具、Agent Loop、权限审批和命令执行都将在本功能形成的配置、协议、会话、事件和 TUI 基础上扩展。

## 目标

- 打通 LLM API 调用，能够向大模型发起请求并正确接收回复。
- 同时支持 Anthropic Messages API 与 OpenAI Responses API，通过同一份配置选择接入对象。
- 支持为所选协议指定自定义服务端地址，但自定义端点必须与声明的协议兼容。
- 提供终端用户界面，承载 Provider 选择、输入、多轮对话、等待状态和流式输出。
- 回复以流式文本增量实时呈现，结束后使用 Markdown 重新渲染并定型展示。
- 在单次进程内维护连续多轮对话所需的可见历史和协议内部状态。
- 对模型调用失败提供可理解、可恢复的错误反馈，不因单次失败退出应用。
- 为以后增加 Tool Calling 提供协议无关的 LLM 与流事件抽象，但本期不实现任何工具。

## 功能需求

### F1：配置加载

系统从项目内的 YAML 配置文件读取非空 `providers` 列表。每个 Provider 包含：

- 唯一且可读的名称。
- 协议类型。
- 可选的自定义端点地址。
- 用于读取密钥的环境变量名。
- 模型名称。
- 是否启用扩展思考。

系统在进入 TUI 前完成配置校验。以下情况视为启动错误：

- 配置文件不存在或无法读取。
- YAML 格式错误。
- Provider 列表为空。
- Provider 名称为空或重复。
- 协议类型未知。
- 模型名称为空。
- 自定义端点不是有效的 HTTP/HTTPS 地址。
- 密钥环境变量名为空，或对应环境变量不存在/为空。

错误应以清晰文本显示并终止启动，不输出未处理堆栈或秘密。

### F2：Provider 选择

若只有一个 Provider，系统直接采用它进入对话。若有多个 Provider，系统在启动后显示方向键选择列表，至少列出每项的名称、协议和模型。

用户确认后，该 Provider 成为当前进程内唯一活动 Provider。用户可以通过 Esc 或 Ctrl+C 取消选择并安全退出。会话中途不切换 Provider。

### F3：多协议适配

V1 明确支持以下协议类型：

- `anthropic`：Anthropic Messages API。
- `openai-responses`：OpenAI Responses API。

自定义 `base_url` 只替换所声明协议的默认端点，不表示系统会自动检测、转换或兼容其他 API 形状。只支持 Chat Completions 而不支持 Responses API 的服务不属于 `openai-responses`。

两个协议适配器分别负责：

- 请求构造。
- 系统提示词映射。
- 历史与协议状态映射。
- 扩展思考参数。
- 流事件解析。
- 错误分类。

上层只依赖协议无关的对话请求、文本增量、完成和错误事件。

### F4：发起对话请求

用户提交消息后，系统将内置系统提示词、当前已提交的对话上下文以及协议延续多轮对话所需的内部状态交给活动 Provider，并发起一次流式请求。

内置系统提示词至少要求模型：

- 将自己识别为 Star Code 的终端助手。
- 默认使用用户当前语言回复。
- 可以使用 Markdown。
- 当前阶段仅能聊天，不得声称已经读取、修改或执行本地项目内容。

当 `thinking=true` 时，协议适配器应以该协议支持的方式请求扩展思考；如果服务端或模型拒绝该设置，应作为清晰的请求错误处理，不得静默伪装成已启用。

### F5：流式接收

系统以流式方式接收 Provider 响应，识别正文文本增量、思考/推理相关事件、完成事件和错误事件。

正文文本增量应尽快输送给界面。思考/推理内容：

- 不向用户渲染。
- 不混入助手正文。
- 不写入普通日志。
- 对后续多轮协议必须使用的 item、签名、ID 或不透明状态，应在内存中保留并由对应协议适配器正确回传。

### F6：多轮上下文

系统在单次进程内维护：

- 用户可见的对话历史。
- 发给模型的协议无关会话历史。
- Provider 维持多轮连续性所需的不透明内部状态。

每轮成功完成后，用户消息和助手最终正文加入已提交上下文。程序退出后，全部历史和协议状态丢弃。

若一轮请求失败：

- 用户消息和错误继续显示在界面历史中。
- 不创建虚假的助手消息。
- 失败轮默认不提交到下一轮模型上下文。
- 用户可以重新输入消息继续会话。

当 Provider 返回上下文过长错误时，系统显示可恢复错误并保持应用可用；本期不自动删除、截断或压缩历史。

### F7：终端界面布局

进入对话界面后，自上而下包含：

1. 启动横幅：ASCII 猫咪、应用名、版本号和当前工作目录。
2. 就绪/运行状态行，不显示本期未实现的工具或 MCP 状态。
3. 对话区，按时间顺序展示用户输入、助手回复和错误消息。
4. 底部带边框的多行输入框，包含 `❯` 提示符和 `Send a message...` 占位文字。
5. 底部状态栏，左侧显示活动 Provider 名称，右侧显示模型名称。

Provider 选择界面和聊天界面都应响应终端尺寸变化。内容超过可用高度时，对话区和选择列表可以滚动。

### F8：流式呈现与 Markdown 定型

流式期间，正文按接收到的文本增量追加显示，不要求把网络增量人为拆成逐字符动画。界面刷新不得阻塞网络接收。

该轮成功结束后，系统使用完整正文重新进行 Markdown 渲染并替换流式临时展示。至少正确处理：

- 普通段落。
- 标题和强调。
- 有序及无序列表。
- 行内代码。
- 围栏代码块。

重新渲染后应尽量维持当前滚动位置；如果用户正在查看底部，则继续保持自动跟随最新内容。

### F9：输入与提交

用户可以在输入框中编辑多行文本：

- Enter 提交非空消息。
- Alt+Enter 插入换行。
- 若当前终端无法区分 Alt+Enter，应提供并在界面提示备用组合键 Ctrl+J。
- 空白消息不得提交。
- 提交后清空输入框。

等待和流式期间不接受新的消息提交，但仍允许滚动、调整终端尺寸和触发退出。

### F10：退出

空闲状态下输入 `/exit` 或按 Ctrl+C，应安全退出程序。

Provider 选择阶段按 Esc 或 Ctrl+C，应取消选择并退出。

请求进行中按 Ctrl+C，应终止当前流式请求并退出整个程序。V1 不提供“只取消当前回复但保留会话继续聊天”的独立功能。

任何退出路径都必须关闭活动网络流、停止计时器、结束后台任务并恢复终端状态。

### F11：错误反馈

当请求失败时，系统在对话区以区别于普通助手消息的样式展示错误，并回到可输入状态。错误至少区分：

- 鉴权失败。
- 限流。
- 网络连接失败。
- 请求或流超时。
- 模型不存在或不可用。
- 请求参数无效。
- 上下文过长。
- 服务端错误。
- 无法识别的流事件或协议错误。

错误信息不得包含完整密钥、Authorization header 或代理凭据。本期不自动重试。

### F12：响应计时

用户消息提交并开始等待 Provider 时立即启动计时。

首个正文增量到达前，状态行显示动画和已用秒数，例如：

```text
Imagining… (5s)
```

收到正文增量后继续计时。本轮成功或失败结束后停止计时，并在该轮记录中显示总耗时。计时刷新不得阻塞流事件处理。

## 非功能需求

### N1：界面不阻塞

网络请求、流事件解析和 Markdown 处理不得运行在阻塞 UI 事件循环的路径上。等待与流式期间界面应继续处理重绘、滚动、尺寸变化和退出事件。

### N2：流式实时性与等待反馈

从请求发出到收到首个正文增量期间，界面持续显示等待动画和递增秒数。正文增量到达后，应在下一次正常 UI 刷新周期内可见，不进行不必要的批量等待。

### N3：跨协议一致体验

无论活动 Provider 使用 `anthropic` 还是 `openai-responses`，用户感知的提交、等待、流式正文、Markdown 定型、错误展示和多轮行为保持一致。协议特有事件不得泄漏到 UI 层。

### N4：配置健壮性

配置文件缺失、YAML 损坏或字段校验失败时，系统给出包含字段位置或 Provider 名称的可读提示，而不是未处理异常堆栈。

### N5：密钥安全

真实 API Key 只能从配置指定的环境变量读取。密钥不得写入示例配置、界面、对话历史或普通日志；异常信息在展示前必须脱敏。

### N6：终端兼容与自适应

在 Windows Terminal、PowerShell 主机以及常见 ANSI 兼容终端中提供合理体验。布局和 Markdown 渲染随宽度调整；窄屏可以折行或简化状态栏，但不得破坏输入和退出功能。

### N7：退出整洁

正常退出、配置选择退出、等待阶段退出、流式阶段退出以及未处理运行时错误都必须通过统一清理路径恢复终端模式和光标状态。

### N8：可测试性

协议适配、会话状态和 TUI 状态转换必须可以使用 Fake Provider 和确定性流事件测试。默认测试套件不得要求真实 API Key 或外部网络。

## 不做的事

- 工具调用或 Function Calling：不发送工具定义、不解析或执行工具调用。
- MCP 集成。
- 文件读取、搜索、编辑或命令执行。
- 权限系统。
- 上下文摘要、自动截断或压缩。
- 长期记忆或跨会话记忆。
- 会话持久化、重启恢复或续聊。
- 除 `/exit` 外的可扩展 Slash 命令体系。
- 会话中途切换 Provider 或模型。
- 向用户展示 thinking/reasoning 内容。
- “取消当前回复但继续会话”的功能；Ctrl+C 只用于退出程序。
- 自动重试和限流退避。
- 通过命令行参数覆盖模型、协议等普通配置。
- 从 YAML 明文读取 API Key。
- OpenAI Chat Completions 兼容协议；自定义 OpenAI 端点必须支持 Responses API。
- Token、缓存命中或费用统计。
- 图片、音频等多模态输入。

## 验收标准

### AC1：单 Provider 启动

仅配置一个有效 Provider 时，程序不显示选择器，直接进入聊天界面，状态栏显示其名称与模型。对应：F1、F2。

### AC2：配置错误

配置缺失、YAML 损坏、Provider 为空、名称重复、协议未知、模型为空、端点非法或密钥环境变量缺失时，启动显示明确错误并退出；输出不包含完整秘密或未处理堆栈。对应：F1、N4、N5。

### AC3：多 Provider 选择

配置多个有效 Provider 时出现方向键列表；用户选择后进入聊天界面并显示所选名称与模型；按 Esc 或 Ctrl+C 可安全取消并退出。对应：F2。

### AC4：Anthropic 协议适配

使用 Fake/Mock Anthropic 服务时，请求包含正确系统提示词、模型、历史和 thinking 设置；文本增量被转换成统一正文事件，协议错误被分类。对应：F3–F5。

### AC5：OpenAI Responses 协议适配

使用 Fake/Mock Responses 服务时，请求包含正确 instructions、模型、历史或会话关联状态和 reasoning 设置；正文事件被统一转换，协议错误被分类。对应：F3–F5。

### AC6：自定义端点

两个协议分别配置兼容的自定义 `base_url` 时，请求发送到对应地址；只支持 Chat Completions 的端点作为 `openai-responses` 使用时，显示协议错误而非错误解析为正常回复。对应：F3。

### AC7：Thinking 不展示但状态保留

Fake 流同时发送思考事件和正文事件时，对话区及普通日志只出现正文；下一轮请求仍包含该协议要求回传的签名、item 或不透明状态。对应：F5、F6、N5。

### AC8：多轮上下文

使用确定性 Fake Provider 完成两轮对话后，捕获的第二轮请求包含第一轮已提交用户消息、助手正文以及必要协议状态；退出并重新启动后上下文为空。对应：F4、F6。

### AC9：失败轮上下文

一轮请求失败后，界面保留用户消息和错误，但下一轮发送上下文不包含虚假的助手回复或默认重复提交失败轮。对应：F6、F11。

### AC10：界面布局

聊天界面包含猫咪 Banner、应用名和版本、工作目录、状态行、对话区、带提示符及占位文字的输入框和 Provider/模型状态栏。对应：F7。

### AC11：流式与 Markdown

Fake Provider 分批发送正文增量时，文本在完成前逐批可见；完成后同一内容以 Markdown 定型，代码块、列表、强调和行内代码正确呈现。对应：F5、F8、N2。

### AC12：多行输入

Alt+Enter 或声明的备用组合键插入换行，Enter 提交，提交后输入框清空；空白消息不会产生请求；流式期间无法提交第二条消息。对应：F9。

### AC13：响应计时

Fake Provider 延迟首个正文增量时，等待动画和秒数立即出现并持续更新；收到增量后计时继续；成功与失败结束时均记录总耗时。对应：F12、N2。

### AC14：请求错误恢复

分别模拟鉴权、限流、网络、超时、模型不存在、无效参数、上下文过长和服务端错误；每次均在对话区显示可区分错误，应用返回可输入状态且不自动重试。对应：F11。

### AC15：界面非阻塞

等待首包和持续流式期间，测试仍可触发 UI tick、滚动、终端 resize 和退出事件，且事件在规定测试超时内被处理。对应：N1。

### AC16：跨协议一致状态

向两个协议适配器输入语义等价的标准化流场景时，TUI 获得相同的等待、正文增量、完成和错误状态转换。对应：N3。

### AC17：密钥脱敏

测试密钥同时出现在配置环境、模拟服务异常和 header 信息中时，启动错误、对话区和测试日志均不包含完整值。对应：N5。

### AC18：终端宽度适配

在预设宽、中、窄三种终端尺寸的渲染测试中，输入框保持可用，正文合理折行，状态栏不会覆盖输入区域；窗口 resize 后布局重新计算。对应：N6。

### AC19：退出恢复

分别从 Provider 选择、空闲、等待首包和流式阶段触发退出；程序停止活动请求及计时器，退出后终端 raw mode、光标和输入回显恢复正常。对应：F10、N7。

### AC20：默认离线测试

移除真实 API Key 并禁止外部网络后，配置、协议映射、会话状态、流式事件和 TUI 状态测试仍能确定性运行；真实 Provider smoke test 仅在显式启用时执行。对应：N8。

## 审批关注点

进入 `plan.md` 前，请确认：

1. V1 只支持 `anthropic` 和 `openai-responses`，暂不支持 Chat Completions 兼容端点。
2. API Key 只通过 YAML 指定的环境变量读取，不允许明文写入 YAML。
3. thinking/reasoning 不展示，但协议要求的内部状态会在内存中保留。
4. Ctrl+C 在请求期间会终止请求并退出整个程序，不提供取消后继续聊天。
5. 完整 TUI、多 Provider 选择和 Markdown 定型均属于 Feature 001 范围。
6. 本功能完成后仍不是 Coding Agent；文件工具和 Tool Loop 将在后续 Feature 中实现。
